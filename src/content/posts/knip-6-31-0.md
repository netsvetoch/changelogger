Вышел минорный релиз [Knip 6.31.0](https://github.com/webpro-nl/knip/releases/tag/knip%406.31.0) — инструмента для поиска неиспользуемых файлов, зависимостей и exports в JavaScript- и TypeScript-проектах. Главное изменение версии — базовый plugin `marko` для проектов на Marko 5 и 6: Knip начинает видеть `.marko`-шаблоны, production entry из каталогов `components`/`tags`, поля `marko-tag.json` и custom tags, которые подключаются без явного import через Marko auto tag discovery.

Источники: [GitHub Release](https://github.com/webpro-nl/knip/releases/tag/knip%406.31.0), [compare 6.30.0…6.31.0](https://github.com/webpro-nl/knip/compare/knip%406.30.0...knip%406.31.0), PR [#1914](https://github.com/webpro-nl/knip/pull/1914) (@caseycarroll), коммиты [feat Marko](https://github.com/webpro-nl/knip/commit/c6b151642701f9b4864ddb5ea8e40580623f59d1), [Array.from](https://github.com/webpro-nl/knip/commit/5aadf47a22bdfd43bb8ad4082768e07fe37fc5ca), [release-it](https://github.com/webpro-nl/knip/commit/6fa9c269c65c0923965924226a5ccf0778842967), [@types/vscode](https://github.com/webpro-nl/knip/commit/6d8e9bf5200cf982d0bc801469c4e2be5627e5b8). ## Плагин `marko`: когда включается и что сканирует

Plugin регистрируется под именем `marko` в `Plugins`, schema (`schema.json` / `pluginsSchema`) и `PluginName`. Enabler — зависимость `marko` в манифесте workspace:

```ts
const enablers = ["marko"];
const isEnabled: IsPluginEnabled = ({ dependencies }) =>
  hasDependency(dependencies, enablers);
```

Конфиг-файлы plugin:

```ts
const config = ["**/marko.json", "**/marko-tag.json"];
```

Production entry строятся из discovery-каталогов `components` и `tags` с паттернами:

- `**/*.marko`
- `**/{component,component-browser}.{js,jsx,ts,tsx,mjs,cjs,mts,cts}` и `**/*.{component,component-browser}.…`
- `**/style.{css,less,scss,sass,styl,stylus}` и `**/*.style.…`

То есть для Marko-компонента Knip учитывает не только template, но и companion scripts/styles рядом с ним — как это принято в структуре Marko tags.

`resolveConfig` различает два случая:

1. **`marko.json`** — каталог конфига попадает в production entry через те же tag-паттерны (`toProductionEntry`).
2. **`marko-tag.json`** — из определения тега резолвятся строковые поля `template`, `renderer`, `parse`, `migrate`, `transform`, `analyze`, `translate` (`toDeferResolve` относительно `configFileDir`).

Тип полей зафиксирован в `MarkoTagDef`:

```ts
export type MarkoTagDef = {
  template?: string;
  renderer?: string;
  parse?: string;
  migrate?: string;
  transform?: string;
  analyze?: string;
  translate?: string;
};
```

Пример из fixture: `src/components/fruit-basket/marko-tag.json` с `"transform": "./transform.ts"` удерживает `transform.ts` в графе; соседний `seasonal-price-helper.ts` без ссылок остаётся unused file.

Включение compiler для `.marko` происходит только если в dependencies есть `marko`: plugin вызывает `getTaglibDependencies(cwd)` и регистрирует `createCompiler(tagDependencies, fallbackDependencies)` на extension `.marko`.

## Compiler `.marko`: imports, styles, tags

`packages/knip/src/plugins/marko/compiler.ts` — sync compiler, который превращает Marko-source в текст, пригодный для oxc-parser / dependency graph Knip.

На выходе всегда синтетический `import "marko";`, затем:

1. **tag-зависимости** — по HTML-тегам (`htmlTagMatcher`) и naive concise-синтаксису (`conciseTagMatcher`) подставляются `import "<pkg>";` из map tag → packages;
2. **styles** — блоки `<style …>` (через общий `styleExtractor`) и concise `style.lang { … }` компилируются less/scss/stylus compilers; для SCSS/Sass по умолчанию;
3. **sanitize** исходника — markup-строки и tag-imports вида `import X from "<tag-name>"` (в т.ч. multiline и `with { load: … }`) вычищаются; префиксы `server` / `client` / `$` / `static` снимаются с script-строк; локальные `export interface` / `export type` / `export const` / `export { … }` без `from` нейтрализуются; анонимный `class { … }` становится `class MarkoComponent { … }`, чтобы парсер видел class body и dynamic `import()` внутри методов.

Что compiler **сохраняет** как module graph (по unit-тестам `marko-compiler.test.ts`):

```marko
import defaultValue, { namedValue } from "./shared.ts"
server import { serverValue } from './server.ts'
client import type { ClientValue } from "./client.ts";
static import staticValue from "./static.ts";
import LocalTag from "./local-tag.marko"
export { exportedValue } from "./exported.ts";
export type { ExportedType } from "./exported-type.ts";
```

После sanitize префиксы Marko исчезают, а обычные ESM import/re-export остаются. Напротив, discovery-import тегов удаляется:

```marko
import EbayButton from "<ebay-button>";
import HeavyChart from "<heavy-chart>" with { load: "visible#chart" };
```

Их «использование» для package graph идёт не через module specifier `<…>`, а через scan имён тегов в markup + taglib map (см. ниже).

Комментарии HTML/`//`/`/* */` вырезаются до анализа, поэтому `import` внутри комментариев и attribute-only строки вроде `title='import ignored from "attribute-only"'` не создают ложных references.

Concise syntax покрыт «наивно» (regex по строкам), не полным Marko parser — в PR прямо сказано, что follow-up возможен, если community понадобится более строгая поддержка.

После merge follow-up commit заменил spread `Set` на `Array.from(dependencies, …)` при сборке synthetic tag imports — поведение то же, совместимость/стиль итерации по `Set`.

## Auto tag discovery и `marko.json` в node_modules

Отдельный модуль `taglibs.ts` закрывает [Marko custom tags / auto discovery](https://markojs.com/docs/reference/custom-tag): пакеты из `dependencies` / `devDependencies` / `peerDependencies` / `optionalDependencies` сканируются на `node_modules/<pkg>/marko.json` (поиск вверх по родителям cwd).

Парсинг `marko.json` **намеренно узкий** — только:

- `exports` (string) — каталог тегов;
- `tags-dir` (string) — legacy-каталог тегов.

Если ни одного из этих полей нет (пустой объект, только `taglib-imports`, битый JSON и т.п.), пакет кладётся в `fallbackDependencies` и считается **used без поиска usages в коде**. Так plugin не ломается на deprecated mechanisms вроде `taglib-imports`, которые Marko планирует убрать: dependency не уходит в false-positive unused, даже если конкретные tag names в project markup не встречаются.

Для `exports` / `tags-dir` plugin читает каталог и строит map **tag name → [packageName, …]**:

- файл `berry-badge.marko` или dir `berry-badge/` с `index.marko` / `berry-badge.marko`;
- вложенный один уровень (кроме самих `tags`/`components` как промежуточных dir names).

Compiler потом, увидев в markup `<berry-badge …/>` или concise-строку, добавляет synthetic `import "@orchard/marko-tags";`.

### Что показывает fixture `plugins/marko`

Интеграционный тест ожидает:

| package.json dependency                                                     | Результат                     |
| --------------------------------------------------------------------------- | ----------------------------- |
| `@orchard/marko-tags` (`exports`, tag `berry-badge` используется)           | used                          |
| `legacy-marko-tags` (`tags-dir`, tag `legacy-banner` используется)          | used                          |
| `combined-marko-tags` (только `taglib-imports` → fallback)                  | used без scan                 |
| `@orchard/unused-marko-tags` (`exports`, tag `pear-banner` не используется) | **unused dependency**         |
| `@orchard/unused-legacy-marko-tags` (`tags-dir`, не используется)           | **unused dependency**         |
| `unused-library` (нет marko.json)                                           | **unused dependency**         |
| `marko`, `sass`, `@marko/type-check` (bin `mtc` в scripts)                  | used / не в dependency issues |

Плюс unused file: `src/components/fruit-basket/seasonal-price-helper.ts`. Счётчики fixture: `dependencies: 3`, `files: 1`, `processed/total: 11`.

Типичный markup, который plugin «видит»:

```marko
import { formatWeight } from "../../util/format-weight.ts";
import FruitSummary from "../../fragments/fruit-summary.marko"
import DiscoveredLabel from "<fruit-label>"

<div.fruit-basket onClick("toggle")>
  <berry-badge count=input.weight/>
  <berry-tally berries=input.weight/>
  <fruit-label label=formatWeight(input.weight ?? 0)/>
  <legacy-banner/>
  <FruitSummary/>
</div>

style.scss {
  @use "../../styles/palette";
  .fruit-basket { color: palette.$ink; }
}
```

Здесь удерживаются: local Marko/TS imports, SCSS `@use`, package `@orchard/marko-tags` через tag `berry-badge`, `legacy-marko-tags` через `legacy-banner`, а также сам runtime `marko`. Tag import `"<fruit-label>"` с module graph снимается sanitize-ом; локальный tag `fruit-label` живёт как production entry в `components/`.

Отдельно plugin подхватывает `server import { … }` в fragments:

```marko
server import { summarizeFruit } from "../util/summarize-fruit.ts"

<p>${summarizeFruit()}</p>
```

## Конфигурация в Knip

В JSON schema добавлен ключ plugin:

```json
"marko": {
  "title": "marko plugin configuration (https://knip.dev/reference/plugins/marko)",
  "$ref": "#/definitions/plugin"
}
```

Как и у остальных plugins, можно точечно включать/выключать или сужать entry/config через стандартный shape plugin config Knip. Отдельного reference MDX на docs-сайте в дереве `knip@6.31.0` под путь `reference/plugins/marko` в diff релиза нет — URL в schema заложен как канонический, сам plugin уже в runtime/schema/tests. В PR также отмечено, что в docs list plugins добавлены `marko` и ранее пропущенный OpenClaw.

## Прочие изменения релиза

Остальные коммиты 6.30.0…6.31.0 — инфраструктура monorepo, не runtime-поведение CLI для большинства пользователей:

- **release-it** root devDependency `^21.0.0` → `^21.0.1`; в `scripts/release.sh` flags `--git.commitArgs=--amend --no-edit` разведены на два отдельных `--git.commitArgs=…` (совместимость с новым CLI release-it).
- **vscode-knip**: `@types/vscode` downgrade с `^1.125.0` на `~1.95.0`, чтобы types совпадали с `engines` range расширения.

Breaking changes в release notes нет.

## Кому обновляться

Имеет смысл ставить 6.31.0, если:

1. в workspace есть `marko` и `.marko` / tag libraries — раньше Knip почти наверняка не видел template imports, SCSS-in-Marko и auto-discovered tags, из-за чего копились false unused files/deps;
2. вы публикуете или потребляете packages с `marko.json` (`exports` / `tags-dir`) и хотите, чтобы unused tag libraries всплывали как dependency issues;
3. используете `marko-tag.json` с `transform` / `renderer` / другими hook-полями — они теперь входят в defer-resolve graph.

Ограничения «basic support», о которых стоит помнить:

- concise syntax — regex, не полный parser;
- из `marko.json` читаются только `exports` и `tags-dir`; deprecated `taglib-imports` и прочее → package = used (fallback), без fine-grained tag usage;
- plugin включается наличием dependency `marko`, не ручным opt-in по умолчанию для non-Marko проектов.

## Обновление

```bash
pnpm add -D knip@6.31.0
# или
npm i -D knip@6.31.0

pnpm knip
# при необходимости сузить/отладить только Marko:
pnpm knip --include dependencies,files,unlisted,unresolved
```

После обновления в Marko-проекте прогоните полный `knip` и сверьте:

1. не «ожили» ли ранее ignored `.marko` / companion `component.ts` / `style.scss`;
2. не пометились ли tag libraries без `exports`/`tags-dir` как used только из-за fallback — при желании сузьте dependencies или дождитесь более строгого follow-up;
3. unused files вроде helper рядом с tag без ссылки из `marko-tag.json` / template — это ожидаемое ужесточение графа, а не регресс.
