Вышел минорный релиз [Knip 6.33.0](https://github.com/webpro-nl/knip/releases/tag/knip%406.33.0) — инструмента для поиска неиспользуемых файлов, зависимостей и exports в JavaScript- и TypeScript-проектах. В этой версии появился типизированный хелпер `defineConfig` на отдельном entrypoint `knip/config`, корректный резолвинг манифестов пакетов под Yarn PnP, а также подготовка к content mappers из грядущего TypeScript 7.1. Плюс серия фиксов плагинов (`vitest`, `webpack`, `nuxt`, `oxlint`) и уточнения в анализе доступов к enum.

Источники: [GitHub Release](https://github.com/webpro-nl/knip/releases/tag/knip%406.33.0), PR [#1946](https://github.com/webpro-nl/knip/pull/1946), [#1960](https://github.com/webpro-nl/knip/pull/1960), [#1973](https://github.com/webpro-nl/knip/pull/1973), [#1978](https://github.com/webpro-nl/knip/pull/1978), [#1981](https://github.com/webpro-nl/knip/pull/1981), [#1982](https://github.com/webpro-nl/knip/pull/1982), [#1983](https://github.com/webpro-nl/knip/pull/1983), [#1984](https://github.com/webpro-nl/knip/pull/1984). Отдельный коммит `74954c2` реализует контекст из issue [#1966](https://github.com/webpro-nl/knip/issues/1966). Версия `6.33.0` — minor-граница semver; `featured` оставлен `false`.

## `defineConfig` на entrypoint `./config`

PR [#1960](https://github.com/webpro-nl/knip/pull/1960) добавляет новый отдельный entrypoint `knip/config` с хелпером `defineConfig` (закрывает issue [#1941](https://github.com/webpro-nl/knip/issues/1941)):

```ts
// knip.ts
import { defineConfig } from "knip/config";

export default defineConfig({
  entry: ["src/index.ts"],
  project: ["src/**/*.ts"],
});
```

Отдельная точка входа нужна, чтобы хелпер и его тип резолвились по одному specifier: существующая карта `.` не меняется, и при загрузке конфига из index-файла ничего лишнего не подтягивается. `./session` уже был прецедентом второго entrypoint, так что форма совпадает.

`defineConfig` возвращает свой аргумент без изменений — на runtime это только типы. Тип `KnipConfig` расширяет как объектную форму, так и синхронную/асинхронную функции, поэтому перегрузки не нужны:

```ts
type KnipConfig =
  | RawConfiguration
  | ((options: ParsedCLIArgs) => RawConfiguration | Promise<RawConfiguration>);
```

По сути это альтернатива `satisfies KnipConfig` для тех, кому удобнее вызов импортированного хелпера. В репозитории проверили, что `knip/config` резолвится потребителем при `moduleResolution: nodenext`, типы приходят из emitted declaration (а не «размываются»), и неверный пример `entry: 42` падает с базовым `string | string[] | undefined`. В `npm pack` попадают `dist/config.js` и `dist/config.d.ts`.

## Резолвинг package.json под Yarn PnP

PR [#1946](https://github.com/webpro-nl/knip/pull/1946) чинит чтение манифестов пакетов при работе с Yarn PnP. Прежний код предполагал, что `package.json` лежит под `node_modules`, но Yarn PnP мапит запросы пакетов через `.pnp.cjs`, а внешние пакеты часто хранятся в архивах под `.yarn/cache`. В #1361 предлагался специальный PnP-лоадер, но его не объединили из-за поддержки Yarn-специфичного пути резолвинга.

Вместо этого Knip теперь резолвит манифесты через уже существующий `oxc-resolver`, который понимает yarn pnp. Для каждого workspace создаётся отдельный инстанс `oxc-resolver`, настроенный игнорировать `exports` пакета — это позволяет прочитать `package.json`, даже если он не публично экспортируется. При этом PnP-резолвинг берётся из активного Yarn-runtime (`yarn knip`), а сам Knip `.pnp.cjs` не загружает. Добавлен end-to-end тест, который запускает Knip с активным PnP-runtime фикстуры.

## Поддержка TypeScript content mappers

PR [#1978](https://github.com/webpro-nl/knip/pull/1978) готовит Knip к грядущей фиче TypeScript 7.1 — content mappers, которые позволяют проверять файлы не только TypeScript (MDX, Vue, Ember и т.д.). Теперь Knip понимает, что поле `package` в записи `contentMappers` — это имя npm-пакета, и учитывает его как зависимость.

В плагине `typescript` это реализовано так: `localConfig.contentMappers.map(cm => toDependency(cm.package))` добавляется в список зависимостей, а в тип `TsConfigJson` добавлено `contentMappers?: { package: string }[]`. Пример конфига из фикстуры:

```json
{
  "contentMappers": [
    { "package": "@mdx-js/content-mapper", "extensions": [".mdx"] },
    { "package": "ember-content-mapper", "extensions": [".gjs", ".gts"] }
  ]
}
```

Фича экспериментальная: конфигурация может поменяться до выхода TypeScript 7.1, но серьёзных изменений не ожидается.

Отдельный коммит `74640c0` резолвит процесс content mapper из `package.json#typescript.contentMapper.exec`. Плагин `typescript` теперь читает и `package.json` как конфиг, превращает массив `exec` в shell-команду и маркирует результат как production-вход. Пример из фикстуры:

```json
{
  "typescript": {
    "contentMapper": {
      "exec": ["node", "lib/transform-server.js"],
      "compilerOptions": ["jsxImportSource"],
      "dynamicConfig": false
    }
  }
}
```

Файлы, на которые ссылается mapper-процесс (`lib/transform-server.js`, `lib/parse-frontmatter.js`), больше не отчитываются как unused — в отличие от реально неиспользуемого `lib/unused-plugin.js`.

## Ужесточение валидации конфига

Коммит `d7ac0cf` меняет поведение при конфиге-не-объекте. Раньше файл конфигурации, резолвящийся в функцию, массив или примитив, склеивался через `Object.assign`, который не копирует ни одного собственного enumerable-ключа — получался пустой конфиг, и Knip молча анализировал проект с дефолтами. Особенно коварен был вариант «функция, возвращающая функцию», который принимало старое ретурн-аннотирование в документированном примере динамического конфига.

Теперь `loadResolvedConfigFile` после разворачивания функции проверяет, что результат является объектом (`typeof === 'object'`, не `null`, не массив), и при нарушении бросает `ConfigurationError`:

```
Expected an object as configuration from <configPath>
```

Процесс завершается с кодом 2. Параллельно в динамическом конфиге починили тип: аннотация переменной констрейнит возврат к объекту конфигурации и типизирует параметр `options`.

## Фиксы плагинов

### vitest: array-entries, root-relative setup и promise mocks

PR [#1982](https://github.com/webpro-nl/knip/pull/1982) чинит несколько валидных паттернов конфигурации Vitest:

- `build.lib.entry` мог быть массивом, и Knip передавал массив прямо в `path.join()`, давая runtime-ошибку. Теперь значения нормализуются: поддерживаются одиночные строки, верхнеуровневые массивы и именованные entry со строками или массивами:

  ```js
  export default {
    build: {
      lib: {
        entry: { main: ["./src/main.ts"] },
      },
    },
  };
  ```

- конфигурационные функции, зависящие от `ssrBuild`, раньше вычислялись только с `ssrBuild: undefined`, из-за чего зависимости из SSR-ветки отчитывались как unused. Теперь функция вычисляется с `ssrBuild: undefined`, `false` и `true`.
- `test.globalSetup` резолвился относительно каталога конфигурации, а не фактического `test.root`. Теперь путь считается от эффективного `test.root`, как это делает сам Vitest.

Тип `ViteConfig` тоже обновлён — разрешает массивы в именованных entry.

Коммит `74954c2` (контекст issue [#1966](https://github.com/webpro-nl/knip/issues/1966)) закрывает пропуск unused exports за модульными promise mocks:

```ts
vi.mock(import("../src/pool.js"), () => ({ getPool: () => ({}) }));
vi.mock(import("../src/auto-mocked.js"));
vi.mock(import("../src/import-original.js"), async importOriginal => ({
  ...(await importOriginal()),
}));
```

В контекст плагина добавлен `markImportExpressionHandled`, а плагин `vitest` регистрирует visitor, который распознаёт `vi.mock(import('...'), ...)` (с проверкой, что `vi` реально импортирован из `vitest` и не затенён), помечает import-expression обработанным и добавляет мокаемый модуль как side-effect-import. Раньше exports таких модулей (например `closePool`) отчитывались как unused — теперь сохраняются, включая варианты `auto-mock`, `importOriginal`, `importActual` и затенённый вызов.

### webpack: entry через `import`

PR [#1981](https://github.com/webpro-nl/knip/pull/1981) учит плагин webpack понимать entry-дескрипторы через свойство `import` (раньше распознавался только `filename`), из-за чего `src/main.js` не регистрировался как entry и мог отчитываться как unused:

```js
module.exports = {
  entry: {
    main: { import: "./src/main.js" },
  },
};
```

Поддерживаются и строка, и массив:

```js
import: ['./src/main.js', './src/polyfill.js'];
```

Существующая обработка `filename` сохранена как fallback, а нестроковые значения безопасно отфильтровываются перед резолвингом путей.

### nuxt: строковый `extends` и слои-источники

PR [#1984](https://github.com/webpro-nl/knip/pull/1984): конфиг `nuxt.config.ts` с `extends: './configs/base'` (одиночная строка) обрабатывался посимвольно, из-за чего символы вроде `c`, `o`, `n` отчитывались как зависимости или нерезолвленные пути. Теперь `extends` нормализуется как `string | string[]`, одиночная строка приводится к массиву, и `configs/base.ts` резолвится корректно.

Коммит `db13615` резолвит слои nuxt из всех форм `extends`-записей. Nuxt (c12) принимает слой как строку, кортеж `[source, options]` или объект `{ source }`, а источники может скачивать с префиксами `gh:`, `github:`, `gitlab:`, `bitbucket:`, `http://`, `https://`. Раньше каждая запись уходила в alias-resolver как есть: кортеж или объект бросал исключение и ронял всю конфигурацию, а скачанный источник отчитывался как unlisted-зависимость.

### oxlint: `.oxlintrc.jsonc` и резолверы из `settings`

PR [#1973](https://github.com/webpro-nl/knip/pull/1973): oxlint обнаруживает и `.oxlintrc.json`, и `.oxlintrc.jsonc`, но плагин глоббил только первый. Проект с JSONC-вариантом полностью пропускал конфиг, и все зависимости `jsPlugins` отчитывались как unused. Теперь `.oxlintrc.jsonc` тоже резолвится.

PR [#1983](https://github.com/webpro-nl/knip/pull/1983): `settings` в oxlint ведёт себя так же, как в ESLint. Плагин вроде `eslint-plugin-boundaries` резолвит спецификаторы по имени из `settings['import/resolver']` и требует, чтобы был установлен `eslint-import-resolver-<name>`. Раньше такие резолверы отчитывались как unused. Теперь они резолвятся из `settings` в плагинах oxlint и vite-plus.

## Точность доступа к enum

PR [#1958](https://github.com/webpro-nl/knip/pull/1958) делает computed element access эквивалентным целостному чтению объекта. Раньше `SomeEnum[expr]` отчитывал каждый member как unused, тогда как `Object.values(SomeEnum)` корректно подавлял те же отчёты. Оба — целостное чтение, и статически неизвестно, какие members читаются. Из репродукции в #1956:

| Паттерн доступа                            | Members reported (до) | После |
| ------------------------------------------ | --------------------- | ----- |
| `Object.values(StatusCodeValues)`          | 0                     | 0     |
| `StatusCodeDynamic[Number.parseInt(code)]` | 5                     | 0     |
| `StatusCodeLiteral[3000]`                  | 5                     | 0     |
| `StatusCodeDirect.normal`                  | 4                     | 4     |

Computed access на enum-импорте теперь помечает enum как `enumerated` (аналогично `Object.keys/values/entries` в call visitor). Dot-доступ `Enum.member` и строковый access `Enum['member']` не меняются — они по-прежнему резолвятся к конкретному member, так что реально неиспользуемые members продолжают отчитываться.

Три follow-up-коммита доводят точность:

- `Keep element access precise for number-like enum member names`: `Number()` принимает и `Infinity`, `0x10`, `1e3`, которые TypeScript допускает как имена enum-членов (отклоняя лишь канонические числовые через TS2452). Раньше такие lookups читались как целостное чтение и подавляли все members — теперь они остаются целостным чтением только для тех случаев.
- `Resolve Object.* enum enumeration through import aliases`: `enumerated` ключевался по локальному биндингу и пропускал aliased-импорты — `Object.values(Alias)` по-прежнему отчитывал все members. Теперь ключуется по экспортируемому идентификатору файла-определения.
- `Resolve named string-key access on namespace-qualified enums`: `ns.Enum['member']` вообще не записывал ссылку, поэтому отчитывался каждый member, включая читаемый, — ещё и с фиксом. Именованные ключи теперь резолвятся как `ns.Enum.member`; остальные ключи остаются целостным чтением.

## Прочее

- **Кодирование argv-массивов** (`b79234c`): в `util/scripts.ts` добавлен `toShellCommand`, который оборачивает каждый элемент в одинарные кавычки (`arg.replaceAll("'", "'\\''")`), потому что argv-массивы запускаются без shell и парсер скриптов не должен спотыкаться о пробелы, операторы, glob'ы и расширения. Это затронуло плагин `moonrepo` (команды-массивы в `moon.yml` после подстановки `$workspaceRoot`/`$projectRoot`) и `dotenv` (`fromArgs` теперь возвращает `parsed['--']` напрямую). В тестах round-trip: `['node','lib/server.js; rm -rf tmp']`, `['node','$HOME/server.js']`, `['node',"it's/server.js"]`, `['node','lib/*.js']`.
- **Переменные окружения в exec.ts** (PR [#1979](https://github.com/webpro-nl/knip/pull/1979)): CI-хелпер запуска knip теперь передаёт весь `process.env`, а не только `PATH`, сохраняя такие переменные, как `KNIP_DISABLE_RAW_TRANSFER`.
- **Проверка line endings** (`ddc9fd0`): `pnpm run ci` теперь сверяет концы строк с `.gitattributes` — раньше файл, сохранённый в CRLF, мог пройти незамеченным, потому что formatter'ы пропускают фикстуры, а Git нормализовал его при следующем checkout.
- Обновлены зависимости (в т.ч. bun до 1.4.0), документация отформатирована remark.
