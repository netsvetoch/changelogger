`Ouroboros` выпустил минорный релиз [`v6.105.0`](https://github.com/razzant/ouroboros/releases/tag/v6.105.0). Это первый тег после `v6.103.0` (он же несёт в себе непомеченный `6.104.0`, подхвативший подписку Antigravity/agy из Claudexor 3.5.0). В релиз вошло три спринта: унифицированные аккаунты, подложка делегирования и наблюдаемость ротации квот. Compare [`v6.103.0...v6.105.0`](https://github.com/razzant/ouroboros/compare/v6.103.0...v6.105.0) — 42 коммита, 146 изменённых файлов.

Источники: GitHub Release [`razzant/ouroboros@v6.105.0`](https://github.com/razzant/ouroboros/releases/tag/v6.105.0), release body, compare-дифф и исходники на теге `v6.105.0`. Это обычный tech-релиз с подробным описанием, а не указатель на отдельный официальный анонс.

## Унифицированные аккаунты: единая модель поверх двух движков

Первый спринт (merge `sprint/unified-accounts`) убирает расхождение между движками, которое раньше проявлялось в разном UI аккаунтов. Теперь за модель отвечает гейт именованных профилей в `ouroboros/gateway/claudexor_accounts.py`.

Ключевое — модель работает за фиче-детекцией: если каталог движков нечитаем, поведение fail-closes к прежнему (не падает, а откатывается на старый сценарий). В UI:

- рендерятся все engine-side профили, при этом уходят фиктивные формулировки «Default CLI login» / «Managed by the X CLI» — теперь копия честная («управляется X CLI», если так и есть);
- честный подсчёт семейств `enabled` + `signed_in`, включая отдельное состояние, когда всё отключено;
- тумблер **Enabled** едет на новом тонком PATCH-прокси профилей `credential_profiles` — DELETE/PATCH живут на одном маршруте, и модуль ничего не интерпретирует в хранилище (`/credentials`), то есть «включить» означает именно включить учётную запись, а не логиниться заново;
- **Remove** доступен на каждой строке, поддерживаемой движком, плюс бейдж «next-up».

```py
# ouroboros/gateway/claudexor_accounts.py — переключение Enabled и удаление
# идут через тонкий PATCH/DELETE credential-profile, не через логин
async def api_claudexor_login(request: Request) -> JSONResponse:
    ...
    gateway.create_credential_profile(harness, profile_id)  # только создать
```

## Делегирование: явный пин профиля и честная custody

Делегирование учится закреплять конкретный учётный профиль за субагентом. Пин едет через переменную окружения `OUROBOROS_SUBAGENT_PROFILE`: хранимое каноническое тело (credential body) проезжает как `credentialProfileId` и при ретрае воспроизводится байт-в-байт. Плюс:

- строгий per-subject health для каждой «приколотой» дорожки (lane), в том числе восстановление review-сессии;
- на «Last delegated run» раскрывается custody: запрошенное против применённого (requested-vs-applied);
- на этом спринте закрыта гонка приёма в claudexord (`servingMode`-aware spawn/attach), переформулирован мандат «няни» в момент диспатча и типизированные оси `capability_delta` передаются через `route_health` двигателю.

## Видимая ротация: типизированные факты и честный терминал

Спринт `sprint/rotation-visibility-20260817` делает состояние дорожки типизированным и видимым от подложки до рендера:

- состояние лейна теперь типизированное: `{failure_code, reset_at, http_status}` плюс `capability_delta` доезжают от substrate до render;
- review-панели считают «оплачено» только когда задача реально диспатчена, а повтор DEGRADED реплеится честно;
- строки health-skip до fanout несут материальную health-эпоху и фингерпринт ростеpа ревьюеров как идентичность повтора;
- `quorum_unreachable` получает честный типовой терминал `blocked_with_evidence` (не бессрочный «висит», а завершён с доказательством);
- ротация квот становится reconcile GET → условный POST с прочным receipt (квитанцией), который никогда не перезаписывает явно сохранённое значение;
- lane history в `supervisor/queue.py` становится видимой, а счётчик запросов/применений честно пересчитывается.

## Инструмент `schedule_followup`: одноразовое отложенное пробуждение

Новый модуль `ouroboros/tools/followup.py` (добавлен в теге) регистрирует одноразовую отложенную задачу через существующий планировщик супервизора — без создания второго планировщика:

- запись в таблицу scheduled-задач `state/scheduled_tasks.json` с триггером `{"type": "once", "run_at": <ISO>}`;
- тик планировщика ставит её один раз как обычную ROOT-задачу (нормальный admission и бюджет), затем помечает запись done;
- за один раз — не более `_MAX_PENDING_FOLLOWUPS = 2` ожидающих; за лимитом — типизированный отказ с раскрытием накопленных записей;
- объектив ограничен `_MAX_OBJECTIVE_CHARS = 4_000`, контекст — `_MAX_CONTEXT_CHARS = 8_000`; у словесного делегируемого субагента нет права чеканить новые ROOT-задачи — только сам агент (типизированный отказ);
- длительность владелец видит/управляет в разделе Schedules (можно выключить или удалить).

```jsonc
// state/scheduled_tasks.json — то, что пишет schedule_followup
{
  "run_at": "2026-08-18T18:00:00Z",
  "type": "once",
  "source": "task_followup",
}
```

```jsonc
// один из параметров инструмента
{
  "name": "schedule_followup",
  "parameters": {
    "properties": {
      "run_at": {
        "type": "string",
        "description": "ISO 8601 instant (naive = UTC)",
      },
    },
  },
}
```

Полезно, когда разумное «время разблокировки» — внешний момент (сброс квоты лейна, эмбарго, медленная зависимость): агент регистрирует отложенное пробуждение, а не сжигает ходы опросом.

## Прочее по диффу

В compare также замечательно: новый модуль `ouroboros/client_surface.py` — per-message «owner surface fact» (гарантированная нормализация браузерной метрики отправки: `pywebview`, `narrow_layout`, `coarse_pointer`, `ua`, `viewport` с жёсткими границами и защитой от `Infinity`, чтобы отказ не ронял сообщение владельца в ws-чате); `subagent_dispatch_notes.py` — типизированный терминал пина, который ни один маршрут не может исполнить; а также правки `agent_startup_checks`/серверной обвязки и smoke-тесты, включая регистрацию `schedule_followup` в ожидаемом наборе инструментов.

## Итог

`Ouroboros 6.105.0` — это согласованный стэк: честная единая модель аккаунтов, пин профиля при делегировании с байт-идентичным повтором и раскрытой custody, а также сквозная наблюдаемость ротации с честными типовыми терминалами (`blocked_with_evidence`) и реальным «разморозь меня позже» через `schedule_followup`. Сборка собрана из коммита [`2d77583a2a16`](https://github.com/razzant/ouroboros/commit/2d77583a2a16d42c10ed3397484cc73792c9ea77); как обычно, артефакты снабжены SBOM/provenance, а проверять подлинность можно через `gh attestation verify`.
